Software engineering contributes four to six questions, and they are some of the most approachable on the exam. A few ask you to trace a short piece of pseudocode and report what it prints. A few ask about complexity: how the running time of a loop or an algorithm grows with the size of its input. The rest test vocabulary and judgement: what polymorphism means, which life-cycle model suits a project, what kind of test checks that modules work together.

You do not need to be a programmer to answer them. You need a disciplined way of tracing code, a feel for Big-O, and clear definitions. All three can be acquired in an evening or two, and the questions then become almost free marks.

## Reading and Tracing Pseudocode

The exam presents code in a neutral pseudocode rather than any particular language. The conventions are intuitive: `for i = 1 to n` includes both end points; `while` loops test their condition before each iteration; indentation shows structure; `div` or `//` usually means integer division and `mod` or `%` the remainder.

The single most valuable technique is to **trace with a table**. Make one column per variable and one row per iteration, and update the values exactly as the code does. Consider:

```
total = 0
for i = 1 to 10 step 3
    total = total + i * i
end for
print total
```

| Iteration | $i$ | $i^2$ | total |
|:-:|:-:|:-:|:-:|
| start | — | — | 0 |
| 1 | 1 | 1 | 1 |
| 2 | 4 | 16 | 17 |
| 3 | 7 | 49 | 66 |
| 4 | 10 | 100 | 166 |

Table: Tracing a loop.

The program prints 166. Notice that the loop includes $i = 10$ because the step lands on it exactly; had the limit been 9, the loop would have stopped after $i = 7$.

::: {.trap}
The commonest tracing errors are off-by-one mistakes at loop boundaries, forgetting that a `while` loop may execute zero times, and confusing integer and real division (`7 div 2` is 3, not 3.5). Tracing in a table, rather than in your head, prevents almost all of them.
:::

### Recursion

A recursive function calls itself on a smaller problem, with one or more **base cases** that stop the recursion. To evaluate one, do not try to hold the whole call tree in your head; build the values **bottom-up** from the base cases. For

```
function f(n)
    if n == 0 return 1
    if n == 1 return 1
    return f(n-1) + 2*f(n-2)
end function
```

compute $f(0) = 1$, $f(1) = 1$, $f(2) = 1 + 2 = 3$, $f(3) = 3 + 2 = 5$, $f(4) = 5 + 6 = 11$, and so on. Each call pushes a **stack frame**; a recursion without a reachable base case exhausts the stack, causing a stack overflow. Naive recursion can also be very wasteful: computing Fibonacci numbers recursively recalculates the same values exponentially many times, which is why **memoisation** or an iterative loop is preferred.

## Algorithm Complexity

**Big-O notation** describes how an algorithm's running time (or memory use) grows as the input size $n$ grows, ignoring constant factors and lower-order terms. An algorithm that takes $3n^2 + 5n + 100$ steps is $O(n^2)$, because for large $n$ the squared term dominates. Figure 15.1 compares the common classes.

![Growth of common complexity classes. For large inputs the differences are enormous: at $n = 1000$, an $O(n\log n)$ algorithm needs about 10 000 steps where an $O(n^2)$ algorithm needs a million.](figures/fig15_bigO.png){width=86%}

| Class | Name | Typical example |
|:--|:--|:--|
| $O(1)$ | Constant | Array access by index; hash-table lookup (average) |
| $O(\log n)$ | Logarithmic | Binary search; balanced-tree lookup |
| $O(n)$ | Linear | Scanning a list; linear search |
| $O(n\log n)$ | Linearithmic | Merge sort; heap sort; efficient average-case sorting |
| $O(n^2)$ | Quadratic | Nested loops over the data; bubble, insertion, selection sort |
| $O(2^n)$ | Exponential | Trying every subset; naive recursive Fibonacci |

Table: Common complexity classes.

### Reading complexity from code

Three rules cover most exam questions:

- **Sequential blocks add**, and the largest term wins: a loop of $n$ followed by another loop of $n$ is $O(n)$.
- **Nested loops multiply**: a loop of $n$ inside a loop of $n$ is $O(n^2)$, even if the inner loop's bound varies with the outer index (as in `for j = 1 to i`, which does about $n^2/2$ steps).
- **A loop variable that is multiplied or divided** by a constant each time runs a logarithmic number of times: `while i > 1: i = i / 2` is $O(\log n)$.

Constant factors vanish: a loop of $10n$ steps is still $O(n)$. Big-O describes growth, not absolute speed.

## Data Structures

Choosing the right data structure is often the most important design decision in a program. Figure 15.2 shows the main ones.

![Common data structures: an array (contiguous, indexed), a linked list (nodes joined by pointers), a stack (last in, first out), a queue (first in, first out) and a binary search tree (left smaller, right larger).](figures/fig15_structures.png){width=95%}

- An **array** stores elements contiguously, so any element can be reached by index in $O(1)$. Inserting or deleting in the middle costs $O(n)$ because elements must shift. In row-major order, element $[i][j]$ of an array with $C$ columns and element size $s$ is at address $\text{base} + (iC + j)s$ (zero-based indices).
- A **linked list** stores elements in nodes joined by pointers. Insertion and deletion are $O(1)$ once you have the position, but finding an element is $O(n)$.
- A **stack** is last in, first out (LIFO), with `push` and `pop`. Stacks manage function calls, undo histories and expression evaluation.
- A **queue** is first in, first out (FIFO), with `enqueue` and `dequeue`. Queues buffer jobs, packets and events.
- A **binary search tree** keeps smaller keys to the left and larger to the right. Search, insert and delete are $O(\log n)$ if the tree is balanced, but degrade to $O(n)$ if keys arrive in sorted order and the tree becomes a chain. Self-balancing trees (AVL, red–black) guarantee $O(\log n)$.
- A **heap** is a tree in which each parent is no smaller (max-heap) or no larger (min-heap) than its children. It finds the largest or smallest element in $O(1)$ and inserts or removes in $O(\log n)$: the natural **priority queue**.
- A **hash table** maps keys to array slots with a hash function, giving $O(1)$ average lookup. Collisions—two keys hashing to the same slot—are handled by chaining or open addressing.
- A **graph** consists of vertices joined by edges, stored as an adjacency matrix or adjacency lists. Breadth-first and depth-first search explore it; Dijkstra's algorithm finds shortest paths.

## Searching and Sorting

**Linear search** checks each element in turn: $O(n)$, and it works on unsorted data. **Binary search** repeatedly halves a *sorted* array: $O(\log n)$, needing at most $\lfloor\log_2n\rfloor + 1$ comparisons. For a million elements, that is 20 comparisons rather than up to a million.

| Algorithm | Best | Average | Worst | Notes |
|:--|:--|:--|:--|:--|
| Bubble sort | $O(n)$ | $O(n^2)$ | $O(n^2)$ | Swaps adjacent pairs; number of swaps = number of inversions |
| Insertion sort | $O(n)$ | $O(n^2)$ | $O(n^2)$ | Excellent for small or nearly sorted data |
| Selection sort | $O(n^2)$ | $O(n^2)$ | $O(n^2)$ | Fewest swaps |
| Merge sort | $O(n\log n)$ | $O(n\log n)$ | $O(n\log n)$ | Stable; needs extra memory |
| Quicksort | $O(n\log n)$ | $O(n\log n)$ | $O(n^2)$ | Fast in practice; worst case with poor pivots |
| Heap sort | $O(n\log n)$ | $O(n\log n)$ | $O(n\log n)$ | In place |

Table: Sorting algorithms.

A sort is **stable** if equal keys keep their original order, which matters when sorting records by one field after another.

## Object-Oriented Programming

Object-oriented design organises software around **objects** that bundle data (attributes) with the operations on that data (methods). A **class** is the template; an object is an instance of it. Four principles define the approach:

- **Encapsulation:** an object hides its internal state and exposes a controlled public interface. Other code cannot corrupt its data directly, and its internals can change without breaking its users.
- **Abstraction:** a class presents only the essential features relevant to its users, hiding unnecessary detail.
- **Inheritance:** a subclass acquires the attributes and methods of a parent class and can extend or override them, expressing an "is-a" relationship (a `Motor` is a `Machine`).
- **Polymorphism:** the same interface invokes different behaviour depending on the object's actual type. Calling `area()` on a list of shapes runs the circle's formula for circles and the square's for squares.

Related ideas: **composition** ("has-a") is often preferred to inheritance for flexibility; **overloading** gives several methods the same name with different parameters; **overriding** redefines an inherited method in a subclass.

## Software Development Life Cycles

A life-cycle model organises the activities of a project: requirements, design, implementation, testing, deployment and maintenance.

- **Waterfall:** each phase completes before the next begins. Predictable and document-driven, it suits projects with stable, well-understood requirements, such as safety-critical systems built to a fixed specification. Its weakness is that problems discovered late are expensive to fix.
- **V-model:** a waterfall variant that pairs each development phase with a test phase, as Figure 15.3 shows. Requirements are validated by acceptance tests, architecture by system tests, detailed design by integration tests and modules by unit tests. It is widely used in regulated industries.
- **Spiral:** repeated cycles of planning, risk analysis, engineering and evaluation, suiting large, high-risk projects.
- **Agile** (for example Scrum): short iterations (sprints) of one to four weeks, each delivering working software, with close customer collaboration and welcoming of changing requirements. It suits projects where requirements are uncertain or evolving.

## Requirements and Design

**Functional requirements** state what a system must do ("the relay shall trip on overcurrent"). **Non-functional requirements** state how well, or under what constraints: performance ("within 50 ms"), reliability, security, usability, maintainability. Good requirements are clear, testable, consistent and traceable to tests.

Good design aims for **high cohesion** (each module does one well-defined job) and **low coupling** (modules depend on one another as little as possible), so that each can be understood, tested and changed independently. Other principles include **modularity**, **information hiding**, and "don't repeat yourself". **Flowcharts** use standard symbols—ovals for start and end, rectangles for processes, diamonds for decisions, parallelograms for input and output—and **UML** diagrams (class, sequence, state, use-case) describe object-oriented designs.

## Testing

Testing happens at several **levels**:

- **Unit testing** checks individual functions or classes in isolation.
- **Integration testing** checks that modules work together through their interfaces.
- **System testing** checks the complete system against its specification.
- **Acceptance testing** checks that the system meets the customer's needs, often by the customer.

And with several **techniques**:

- **Black-box testing** derives tests from the specification, without looking at the code: equivalence partitioning, boundary-value analysis.
- **White-box testing** derives tests from the code's structure, aiming for statement, branch or path coverage.
- **Regression testing** re-runs existing tests after a change to catch unintended side effects; it is ideal for automation.
- **Static analysis** and **code review** find defects without running the program, and are among the most cost-effective quality practices, because defects found early cost far less to fix.

Remember the distinction between **verification** ("are we building the product right?"—does it meet its specification?) and **validation** ("are we building the right product?"—does it meet the user's real need?).

## Version Control and Configuration Management

A **version control system** such as Git records every change to the code, lets developers work on **branches** in parallel and **merge** them, and allows any earlier version to be recovered. **Configuration management** extends this to all project artefacts, ensuring that every released build can be reproduced exactly. **Continuous integration** builds and tests the code automatically every time a change is committed.

## Databases

A **relational database** stores data in **tables** (relations) of rows (records) and columns (fields). Each table has a **primary key** that uniquely identifies each row and must never be null. A **foreign key** in one table refers to the primary key of another, linking them and enforcing **referential integrity**.

**SQL** is the standard language:

- `SELECT name, rating FROM transformers WHERE rating > 500 ORDER BY rating;` retrieves data;
- `INSERT`, `UPDATE` and `DELETE` modify rows;
- `CREATE` and `ALTER` define and change table structure;
- `JOIN` combines rows from related tables on matching keys.

**Normalisation** organises tables to remove redundancy, so that each fact is stored once and updates cannot leave the data inconsistent. Transactions obey the **ACID** properties: atomicity, consistency, isolation and durability.

## Thinking Through an Exam Problem

> *What is printed by the following pseudocode?*
>
> ```
> x = 1
> count = 0
> while x < 100
>     x = x * 3
>     count = count + 1
> end while
> print count, x
> ```

**Trace it.** $x$ takes the values 1, 3, 9, 27, 81, 243, with count rising to 1, 2, 3, 4, 5. After the fifth pass $x = 243$, the condition $x < 100$ fails, and the loop ends.

**Answer.** The program prints `5, 243`.

**Reflect.** The loop runs $\lceil\log_3100\rceil = 5$ times—a logarithmic loop. The traps are stopping one iteration early (reporting $x = 81$, which is still less than 100) or forgetting that the test happens *before* each iteration, not after.

## Common Traps in Software Engineering

**Inclusive loop bounds.** In the exam's pseudocode, `for i = 1 to n` normally includes both 1 and $n$. Count the iterations carefully when the step is not 1; the loop stops at the last value that does not pass the limit.

**Big-O of sequential code.** Two loops of $n$ one after the other are $O(n)$, not $O(n^2)$. Only nesting multiplies.

**Best, average and worst cases.** When a question asks about an algorithm's complexity without qualification, it usually means the worst case. Quicksort is the classic example: $O(n\log n)$ on average, $O(n^2)$ in the worst case.

**Verification and validation.** Verification checks the product against its specification; validation checks it against the user's real needs. The exam may describe a scenario and ask which one is taking place.

**Black-box versus white-box.** If the tester designs tests from the requirements without seeing the code, it is black-box testing. If the tests are designed to exercise particular branches or paths in the code, it is white-box testing.

**Stacks and queues in traces.** When a question lists a sequence of push and pop operations, write the structure's contents after every single operation, with the top or front clearly marked. Doing it in your head invites exactly the reversal the distractors are built to catch.

**Recursion depth versus number of calls.** The depth of recursion (how many frames are on the stack at once) is not the same as the total number of calls. A naive recursive Fibonacci function reaches a depth of only $n$ but makes exponentially many calls, which is why it is slow but does not usually overflow the stack for moderate $n$.
